# Arcade asset retention

Run `python3 scripts/test_retain_arcade_assets.py` (Python standard library only).
Run `python3 scripts/retain_arcade_assets.py merge dist PREVIOUS.zip NEXT.zip`; use `-` for the first snapshot.
The new ZIP contains a versioned SHA256/size manifest and cumulative immutable dependencies. It never contains old HTML, component.js, service workers, headers, config, or documentation. Existing `assets/` runtime extensions, audio MP3s, and version-named Stockfish JS/WASM are retained deliberately. Updating any retained path with different bytes fails; publish the replacement under a new filename.

ZIP metadata, duplicate paths/keys, path traversal, member types/symlinks, hashes, collisions, and declared uncompressed sizes are checked before restoration writes. The current build is authoritative for entry/pages/config. All distribution files must be regular, with at most 20,000 files and 25 MiB per file; header lines must not exceed 2,000 characters. Cumulative uncompressed files also have a 2 GiB CI safety ceiling. ZIP uploads must be strictly below 2 GiB. A snapshot is one asset on its own unique release, well below GitHub's 1,000 assets per release limit. No pruning, overwrite, cache fallback, or external storage is provided; hitting a ceiling stops deployment for an explicit retention-policy decision.

`select-release` consumes the successful paginated GitHub releases response (`gh api --paginate --slurp`). Only absence from a successful listing establishes a first snapshot. The newest published `arcade-assets-RUN-ATTEMPT` release must contain one uploaded snapshot.zip. Retrieval/auth/rate-limit/corruption failures stop the job; incomplete drafts are not published snapshots. A snapshot from a failed deployment is safe to reuse because it is cumulative. Each run creates a new prerelease with the archive attached, before Cloudflare upload; every preceding snapshot remains recoverable. Retention starts with the first opted-in deployment; assets already removed before adoption cannot be reconstructed.

`check-pin` requires the caller's full `uses` SHA and `support-sha` to match the checked-out helper commit. Callers always use canonical `quiet-build/.github`. Update both pins together after reviewing a support commit.

The dedicated reusable workflow installs Node 24 before pnpm 11.25.0 (which requires Node >=22.13), freezes dependencies, runs caller source gates, builds once with `VITE_BASE=/`, then runs component/standalone and applicable budget checks. It preserves Flappy/Defense GitHub Pages using a second job and separate subpath build after the Cloudflare gates/deployment; that build cannot mutate the retained root artifact. The existing unrelated deploy-static-site.yml is unchanged. Deployment is serialized per repository, requires caller contents:write, and only runs on main. PR verification and Neon API publication stay independent.
